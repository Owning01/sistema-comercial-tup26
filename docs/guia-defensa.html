01

Mapa

Qué se construye, qué tenés que poder explicar y por dónde empieza la defensa.

El sistema lo usa el personal de un comercio de un solo local. El vendedor arma la venta en el mostrador, identifica al comprador, elige la forma de pago y emite la factura. En el mismo acto, el sistema descuenta el stock. Si la venta es en cuenta corriente, registra la deuda del cliente.

Son cinco módulos: Inicio con indicadores, Ventas, Productos con existencias, Clientes con cuenta corriente y Usuarios. Dos roles: administrador y vendedor. Una única página pública: /login.

Al terminar esta guía vas a poder:

  • Dibujar el camino completo de una factura, desde el clic hasta el commit.
  • Decir en qué archivo y en qué función vive cada una de las 12 reglas de negocio.
  • Explicar por qué el stock se guarda, el saldo se calcula y el precio se congela.
  • Mostrar con un comando qué pasa si dos vendedores venden la última unidad.
  • Hacer los seis cambios pequeños del enunciado sin ayuda.
  • Publicar y comprobar que la URL usa Turso, no un archivo local.

La ruta de 10 minutos

La demostración oficial pide cuatro operaciones y una verificación después de cada una. Ensayala en este orden:

  1. Entrar como administrador.Mostrar el tablero con ventas del día, del mes y saldos. Es la prueba de que el seed cargó datos.
  2. Vender al consumidor final en efectivo.Un producto, cantidad 1, monto recibido. Mostrar el vuelto y el comprobante.
  3. Verificar el stock.Abrir la ficha del producto y mostrar el movimiento de venta con la existencia resultante.
  4. Dar de alta un cliente y venderle en cuenta corriente.El alta se hace en un modal, sin perder la venta. Mostrar el saldo nuevo y el límite.
  5. Registrar un pago.Importe, medio y observación. Mostrar el recibo numerado y el saldo actualizado.
  6. Anular una factura como administrador.Motivo obligatorio. Mostrar el stock reingresado y el crédito en la cuenta.
  7. Probar un permiso.Entrar como vendedor y llamar a una ruta de administrador. Mostrar el 403, no el botón oculto.
La regla de oro Si no podés decir en qué función se aplica una regla, todavía no la sabés. La defensa no pregunta si el sistema funciona: pregunta dónde está la regla y qué pasa si la sacás.

02

Tesis

Cuatro leyes que ordenan todo el sistema. Si entendés estas, el resto se deduce.

L1

Toda regla vive en un servicio.

La ruta lee la sesión y llama. La página muestra y avisa. El servicio valida, verifica el rol, aplica la regla y abre la transacción. Si una regla aparece en dos lugares, está duplicada.

L2

La base se defiende con invariantes, no con buena voluntad.

La existencia nunca es negativa. El saldo es débitos menos créditos. Una factura se graba completa o no se graba. La numeración no tiene huecos. Cada invariante tiene una única función que lo protege.

L3

El servidor decide; la interfaz anticipa.

Ocultar un botón es una ayuda visual. El permiso lo decide el servicio, que responde 403 aunque la ruta se llame con curl. Lo mismo vale para el stock y el límite de crédito.

L4

Cada dato derivado tiene una sola fuente.

El saldo sale de los movimientos de cuenta. La existencia se guarda, pero solo cambia en moverStock(). El precio y la descripción se copian a la factura para congelarse. Nadie recalcula por su cuenta.

La consecuencia incómoda Un sistema que funciona en el camino feliz no está aprobado. La nota está en los bordes: la última unidad, el pago de más, el vendedor que llama a la API, el usuario desactivado con la cookie abierta.
03

Modelo

Cinco capas, una dirección. La regla baja, el dato sube.

Una mutación recorre el diagrama de arriba hacia abajo. El componente de cliente envía un POST al Route Handler. El adaptador exige la sesión, lee el JSON y llama al servicio. El servicio valida con Zod, verifica el rol, aplica las reglas y abre la transacción. Drizzle ejecuta el SQL. Si algo falla, la transacción vuelve atrás y el adaptador traduce el error a JSON.

Una lectura puede saltar los adaptadores: un Server Component llama directo al servicio y renderiza en el servidor. Eso no debilita la seguridad, porque el servicio sigue verificando el rol. Lo que no se saltea nunca es la capa de servicios.

La razón es práctica: si mañana cambia el límite de crédito, se cambia en una función. Si el mismo control estuviera en la ruta, en la acción y en el formulario, habría que cambiarlo tres veces y una quedaría vieja.

El modelo se lee en dos direcciones. La primera es el catálogo: categorias → productos → movimientos_stock. La segunda es la venta: clientes → facturas → factura_items, con dos ramas que salen de la factura, una hacia el stock y otra hacia la cuenta corriente.

La tabla contadores no está en el modelo mínimo. Se agrega para asignar números sin huecos: guarda el último número por punto de venta y se incrementa dentro de la misma transacción. Si la factura falla, el incremento también se deshace.

No hay tabla de saldos. El saldo de un cliente es la suma de sus débitos menos sus créditos. Tenerlo en dos lugares invita a que se desincronicen; derivarlo tiene un costo de consulta que, para este volumen, es irrelevante.

La frase para la defensa

“La existencia se guarda porque necesito una condición atómica para descontar; el saldo se calcula porque no necesito bloquearlo y así nunca se desincroniza. La suma de movimientos de stock tiene que dar la existencia; la suma de movimientos de cuenta tiene que dar el saldo.”

04

Qué se escribe al confirmar una factura

TablaOperaciónCuándo

Se guarda

  • Existencia: para poder hacer el UPDATE ... WHERE existencia >= ? atómico.
  • Precio y descripción en la factura: para congelar el comprobante.
  • Existencia resultante en cada movimiento: para auditar sin recalcular toda la historia.
  • Total de la factura: para no recalcular precios viejos.

Se calcula

  • Saldo del cliente: débitos menos créditos de movimientos_cuenta.
  • Disponible: límite menos saldo, o nulo si no hay límite.
  • Total adeudado: suma de saldos positivos.
  • Bajo mínimo: existencia menor o igual al stock mínimo.
  • Total emitido: suma de facturas emitidas que cumplen el filtro.

Por qué el saldo no se guarda. Un saldo guardado obliga a actualizarlo en cada venta, cada pago y cada anulación. Si una de esas tres operaciones falla o se agrega una cuarta, el número queda mal y nadie lo nota hasta que el cliente reclama. Derivarlo cuesta una consulta y elimina la clase entera de errores.

Por qué la existencia sí se guarda. El control de concurrencia necesita una condición en el UPDATE: existencia = existencia - ? WHERE id = ? AND existencia >= ?. Si la existencia se calculara sumando movimientos, dos ventas simultáneas podrían leer el mismo total y ambas pasar el control. La columna permite que SQLite decida cuál gana.

La frase para la defensa

“Los importes son enteros en centavos porque un float no representa exactamente los decimales: 0.1 + 0.2 no da 0.3. Con centavos, la suma es exacta y el formato se aplica solo al mostrar.”

Restricciones que evitan errores

  • Únicos: usuarios.email, categorias.nombre, productos.codigo, clientes.nro_doc, facturas (punto_venta, numero), pagos.numero.
  • Índices: productos.categoria_id, productos.activo, facturas.fecha, facturas.cliente_id, movimientos_stock(producto_id, fecha), movimientos_cuenta(cliente_id, fecha), factura_items.factura_id.
  • Bajas lógicas: usuarios, categorías, productos y clientes tienen activo. No hay DELETE para registros con historial.
  • Normalización: documento y teléfono se guardan como dígitos; email en minúsculas; código de producto en mayúsculas. Así el duplicado se detecta antes.
Para la defensa

Corré este script antes de la demo y mostralo. Un sistema que dice “cuadra” no es lo mismo que un sistema que lo demuestra con una consulta.

Migraciones

Base

Archivos SQL generados a partir de la diferencia entre el esquema y la base. Se aplican en orden y quedan registrados en una tabla de control.

Por qué importa

Permiten recrear la base en otra máquina y en Turso sin pasos manuales. Agregar un campo es una migración revisable, no un ALTER TABLE escrito a mano en producción.

Cómo se usa

Se edita schema.ts, se corre pnpm db:generate, se revisa el SQL y se aplica con pnpm db:migrate. Nunca se edita la base publicada a mano.

11

Transacciones

Reglas

Un grupo de escrituras que se confirman juntas o se deshacen juntas. Si una falla, la base vuelve al estado anterior.

Por qué importa

Confirmar una factura escribe cinco tablas. Si se graba la factura y falla el stock, queda un comprobante que no existe en la realidad. La transacción impide ese estado.

Cómo se usa

db.transaction(async (tx) => { … }). Todas las consultas usan tx, no db. Un throw hace rollback. La transacción se mantiene corta.

En el código · src/server/services/facturas.ts

12

Actualización condicional

Reglas

Un UPDATE que solo se aplica si la fila cumple una condición. El número de filas afectadas dice si la operación ganó o perdió.

Por qué importa

Es la forma simple de resolver dos vendedores con la última unidad: ambos intentan descontar, pero solo uno cumple existencia >= cantidad. El otro recibe 409.

Cómo se usa

.set({ existencia: sql`existencia - ${n}` }).where(and(eq(id), gte(existencia, n))). Si rowsAffected !== 1, se lanza STOCK_INSUFICIENTE y la transacción vuelve atrás.

06

Flujos

El código que tenés que poder recorrer con el dedo. Los nombres pueden variar; el orden, no.

Estos son los seis caminos que concentran la defensa. Si entendés el de la factura, entendés el 60% del sistema. Los demás son variantes del mismo patrón: adaptador delgado, servicio con reglas, transacción y respuesta pública.

1. Login y sesión

El login no guarda la contraseña. Compara el hash, firma un JWT y lo deja en una cookie que JavaScript no puede leer. En cada pedido, el usuario se vuelve a buscar en la base.

Las tres barreras

El proxy redirige al login si falta la cookie. El layout vuelve a comprobar que haya un usuario válido. Cada servicio verifica el rol. Las tres son necesarias: la cookie se puede falsificar si el secreto se filtra, y el proxy no consulta la base.

2. Alta de producto con stock inicial

El producto nace con existencia cero. Si viene stockInicial, se registra como un ingreso en la misma transacción. La ruta queda en tres líneas.

3. La única función que mueve stock

Ventas, anulaciones, ingresos y egresos llaman a moverStock(). Ninguna otra función toca la columna existencia. La condición del UPDATE es la que resuelve la concurrencia.

Qué tenés que decir

“La condición existencia >= cantidad está en el WHERE, no en un if previo. Si dos transacciones compiten, SQLite serializa las escrituras y solo una actualiza la fila. La otra recibe cero filas afectadas y se aborta.”

4. Pago de cuenta corriente

El pago graba el recibo y el crédito en la misma transacción. El saldo se consulta antes de aceptar: un pago mayor a la deuda se rechaza con 422 PAGO_SUPERA_DEUDA.

5. Confirmar una factura

Es la operación compuesta del parcial. El cliente manda productos y cantidades, nunca precios. El servidor calcula, controla, numera, graba, descuenta y debita. Todo dentro de una transacción.

  1. Validar el cuerpo.Zod exige al menos un ítem, sin productos repetidos y con cantidades enteras mayores que cero.
  2. Leer el comprador.Si hay clienteId, tiene que existir y estar activo. Si es cuenta corriente, tiene que tenerla habilitada.
  3. Leer los productos y sus precios.Se usan los precios actuales del catálogo, no los que mandó el cliente. Se rechazan los productos inactivos.
  4. Calcular subtotales y total.En centavos enteros. La descripción y el código se copian a la línea.
  5. Controlar la forma de pago.Contado: el monto recibido cubre el total. Tarjeta: solo tipo, marca y últimos 4. Cuenta corriente: el saldo nuevo no supera el límite.
  6. Asignar el número.El contador se incrementa dentro de la transacción. El número real se conoce recién acá.
  7. Grabar factura e ítems.El total y los precios quedan congelados. La factura nace en estado emitida.
  8. Descontar stock y grabar movimientos.Un moverStock() por renglón. Si uno falla, se deshace todo.
  9. Debitar la cuenta.Solo si es cuenta corriente. El saldo se devuelve calculado, no se guarda.
Por qué el cliente no manda precios ni total

Porque el cliente es el navegador, y el navegador se puede manipular. Si el total viniera del cliente, cualquiera podría vender un martillo a un peso. El servidor lee el precio del catálogo, calcula y congela una copia en la factura.

6. Anular una factura

Solo el administrador, con motivo obligatorio. La factura no se borra: pasa a anulada. El stock reingresa con un movimiento de anulación y, si fue a cuenta corriente, se acredita el total.

7. Tablero

Una consulta por indicador, todas sobre facturas emitida. La serie de 30 días se completa en JavaScript para que Chart.js no tenga huecos. Las fechas se agrupan en hora de Argentina.

La frase para la defensa

“El tablero no guarda indicadores: los calcula. Si cambio una factura o la anulo, el próximo request ya muestra el número correcto. No hay un proceso de actualización que se pueda olvidar.”

Cómo se resalta el módulo activo. El componente del sidebar usa usePathname() y compara con la ruta de cada ítem. En móvil, el sidebar se abre en un Sheet de shadcn.

I02¿Dónde se da formato a los importes y a las fechas?

Respuesta corta. En src/lib/formatos.ts: formatearMoneda, formatearFecha, formatearFechaHora, formatearDocumento y formatearNumero.

Por qué un módulo único. Para que la moneda sea $ 12.345,50 en el listado, el comprobante y el recibo. Si cada componente formatea, tarde o temprano uno muestra otra cosa.

Cómo se usa. Intl.NumberFormat("es-AR", …) y Intl.DateTimeFormat("es-AR", { timeZone: "America/Argentina/Buenos_Aires" }). Los componentes no llaman a Intl por su cuenta.

I03¿Dónde se validan los datos de un formulario? ¿Se usan las mismas reglas en el servidor?

Respuesta corta. En src/lib/validaciones.ts. El formulario usa safeParse para mostrar el error junto al campo; el servicio usa parse para cortar con VALIDACION. Es el mismo esquema.

Por qué las mismas. Si el formulario valida una cosa y el servidor otra, el usuario ve un error que el servidor acepta o, peor, el servidor acepta algo que el formulario prohíbe. Una sola definición evita la deriva.

Si te repreguntanLa validación del cliente es una ayuda de UX. La que decide es la del servidor, porque el POST se puede hacer sin pasar por el formulario.

I04¿Cómo se agrega un producto a la venta usando solo el teclado?

Respuesta corta. El buscador tiene el foco al abrir la pantalla. Se escribe el código o la descripción, se elige el resultado con las flechas y se agrega con Enter. Después del alta, el foco vuelve al buscador y la cantidad queda seleccionada.

Atajos. Enter agrega; Tab pasa a cantidad; Esc cierra el modal; Ctrl + Enter abre el pago. Todo con onKeyDown, sin depender del mouse.

Si te repreguntanEl foco tiene que volver al buscador después de agregar. Si se queda en el botón, el vendedor tiene que usar el mouse y la venta deja de ser ágil.

I05¿Qué muestra un listado mientras carga, cuando está vacío o cuando falla?

Respuesta corta. Cargando: un esqueleto con la forma de la tabla. Vacío: un mensaje claro y, si corresponde, un botón para crear el primer registro. Error: un mensaje con la opción de reintentar.

Dónde se ve. loading.tsx o Suspense para la carga; EmptyState y ErrorState en src/components/estados.tsx; un toast para confirmar una mutación.

Si te repreguntanUn listado vacío no es un error. “No hay facturas en este rango” es distinto de “no se pudo conectar”. La interfaz tiene que distinguirlos.

Lo que no se hace

  • No se dice “lo hizo todo la IA”. La defensa es individual y el tribunal puede pedir cualquier archivo.
  • No se commitea el código sin leerlo. Un archivo que no entendés es una pregunta que no podés contestar.
  • No se usa la IA para decidir las reglas de negocio. Las reglas están en el enunciado; la IA las implementa y vos las verificás.
  • No se borra el historial de errores. La corrección es parte de la nota.
